## 一、问题诊断

### 当前问题
各EditorScreen的UiState包含与EntityEditorState重复的字段：

| 重复字段 | CategoryEditorUiState | AddTransactionUiState | EntityEditorState |
|---------|----------------------|---------------------|------------------|
| isLoading | ✅ | ✅ | ✅ |
| isSaving | ✅ | ❌ | ✅ |
| hasUnsavedChanges | ✅ | ❌ | ✅ |
| canSave/saveEnabled | ✅ | ✅ | ✅ |
| showUnsavedChangesDialog | ✅ | ❌ | showDiscardConfirm |
| isEditMode | ✅ | ✅ | ✅ |

### 影响分析
1. **状态同步复杂**：需要手动同步两份相同数据
2. **维护成本高**：修改需要多处更新
3. **易出错**：状态不一致导致UI异常
4. **代码冗余**：约30%的状态管理代码重复

## 二、重构方案：状态分离模式

### 核心原理
将单一的UiState拆分为两个独立的状态流：
- **FormState**：业务数据状态（表单字段、验证错误等）
- **EntityEditorState**：UI元状态（加载、保存、脏值等）

### 架构对比

#### 重构前
```kotlin
data class CategoryEditorUiState(
    // 业务数据
    val name: String = "",
    val type: Category.Type = Category.Type.EXPENSE,

    // UI元状态（重复）
    val isLoading: Boolean = false,
    val isSaving: Boolean = false,
    val hasUnsavedChanges: Boolean = false
)
```

#### 重构后
```kotlin
// 业务数据状态
data class CategoryFormState(
    val name: String = "",
    val type: Category.Type = Category.Type.EXPENSE,
    val nameError: String? = null
)

// UI元状态（复用EntityEditorState）
val editorState = EntityEditorState(
    isLoading = false,
    isSaving = false,
    hasUnsavedChanges = false
)
```

#### 2.2 重构AddTransactionViewModel - 兼容性层方案（✅ 100%完成）

**策略**：采用兼容性层而非完全重构，降低风险（已成功验证）

```kotlin
@HiltViewModel
class AddTransactionViewModel @Inject constructor(...) : ViewModel() {

    // 新架构：分离的状态流
    private val _formState = MutableStateFlow(TransactionFormState())
    val formState: StateFlow<TransactionFormState> = _formState.asStateFlow()

    private val _editorState = MutableStateFlow(EntityEditorState())
    val editorState: StateFlow<EntityEditorState> = _editorState.asStateFlow()

    // 兼容性层：提供旧的uiState以减少修改范围（后续可以逐步移除）
    @Deprecated("使用formState和editorState替代", ReplaceWith("formState"))
    val uiState: StateFlow<AddTransactionUiState> = combine(
        formState,
        editorState
    ) { form, editor ->
        AddTransactionUiState(
            accounts = form.accounts,
            selectedAccount = form.selectedAccount,
            isLoading = editor.isLoading,
            canSave = editor.saveEnabled,
            isEditMode = editor.isEditMode,
            // ... 映射所有字段
        )
    }.stateIn(viewModelScope, SharingStarted.Lazily, AddTransactionUiState())

    init {
        // 监听表单状态变化，自动更新编辑器状态
        viewModelScope.launch {
            formState.collect { form ->
                updateEditorStateFromForm(form)
            }
        }
    }

    /**
     * 根据表单状态更新编辑器状态
     */
    private fun updateEditorStateFromForm(form: TransactionFormState) {
        val hasChanges = hasUnsavedChanges()
        val canSave = form.isValid  // 使用FormState的验证逻辑

        _editorState.value.hasUnsavedChanges = hasChanges
        _editorState.value.saveEnabled = canSave
    }
}
```

**优势**：
- ✅ 现有代码继续使用uiState，无需大规模修改
- ✅ 新代码可以直接使用formState和editorState
- ✅ 降低重构风险，可以渐进式迁移
- ✅ 通过@Deprecated注解标记旧API，鼓励迁移

**劣势**：
- ⚠️ combine操作符有轻微性能开销
- ⚠️ 代码库中会暂时存在两套API

## 六、风险控制

### 潜在风险
1. **状态不同步**
   - 缓解：使用LaunchedEffect监听和同步
   - 验证：单元测试覆盖状态同步逻辑

2. **性能影响**
   - 缓解：使用distinctUntilChanged避免重复更新
   - 监控：Profile工具检测性能回归

3. **迁移中断**
   - 缓解：保留原代码，完成测试后再删除
   - 保护：Git分支隔离，每个Screen独立分支

4. **兼容性层的技术债务**
   - 风险：combine操作符增加复杂度
   - 缓解：通过@Deprecated注解标记，计划逐步迁移
   - 期限：3个月内完全移除兼容性层

### 回滚方案
1. **代码层面**：Git分支隔离，每个Screen独立分支
2. **文件层面**：保留原始文件，添加_OLD后缀
3. **运行时层面**：Feature Flag控制新旧版本切换
4. **数据层面**：状态分离不影响数据库，无需数据迁移
